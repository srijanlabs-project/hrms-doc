# 1. Purpose

This is the working development plan for building the Staffsy Enterprise HRMS from the specification library. It sequences the build into phases with explicit deliverables, spec references, and done-criteria. It complements the wave model in `02-release-slicing-and-priority-waves.md` with implementation-level ordering.

Strategy: desktop-first UI from the template boards; mobile follows with dedicated boards. Modular monolith per the tech-stack ADR (`06-cross-cutting-specs/19`). Every screen is built from its template board — never invented.

Closed a real security gap in the process: Phase 1/2 trusted a client-supplied `X-Tenant-Code` header for every request; AuthGuard now overrides tenant scope with the verified session's tenantId, so a spoofed header can no longer widen access (proven with a live test: a valid acme session sending `X-Tenant-Code: globex` still only sees acme data). Verified end to end: OTP request for real vs. nonexistent accounts returns an identical response (no enumeration), wrong code → generic 401, correct code → 200 + working cookie, wrong role → 403, logout → session revoked and subsequent reuse → 401. Login page has no template board (checked the full registry, genuinely not there) — built from tokens.
- **Phase 4 complete (Leave, first workflow vertical)**: LeavePolicy/LeaveRequest/Notification models under RLS. Balance is deliberately live-computed (pro-rata by months elapsed since joining, minus approved-request days for the current calendar year) rather than a persisted ledger updated by a BullMQ job — no queue infrastructure exists yet (same Docker gap noted in the ADR), and the live calculation is real math against real data, just not queue-backed. Single-level approval only (requestor's direct manager, resolved via Employee.managerId), with org_admin/hr_ops override. Built from three boards: Apply Leave (T-005, single-step, real balance rail), Approvals (T-007, queue + decision panel, real KPI counts), Time Off Calendar (T-008, month grid of own leave). In-app notifications on submit and decision, wired to a real bell dropdown with unread count. T-001's Leave Balance KPI and greeting name are now live. Role-aware nav: the Team/Approvals section only renders for manager/hr_ops/org_admin — a first, partial close of the Phase 3 permission-aware-nav deferral (still only this one item). Caught and fixed a real regression during this phase: the OTP refactor had silently dropped `AuthModule`'s `exports` array, which nothing caught until `LeaveModule` became the first cross-module consumer of `AuthRepository` — surfaced immediately by the "always start the server and verify" discipline, not by typecheck. Verified end to end through the actual browser UI, not just curl: employee applies (T-005) → manager sees it in the approval queue with correct KPI counts (T-007) → approves → balance decrements live → notification bell shows both the submission and decision events → employee's hub and T-001 KPI reflect the new balance. RLS re-verified (18/18) after the new tables.
- **Phase 5 complete (Attendance & Payroll Control)**: AttendanceDay/EmployeeCompensation/PayrollRun/PayrollRunResult models under RLS. Attendance is manual-mark only (Present/Absent/HalfDay, exception-style — a day with no mark defaults to present rather than requiring every day to be marked), reused as `CurrentEmployeeService` was promoted out of the leave module into `people/` so attendance and payroll could both depend on it without a backwards leave→payroll coupling. Payroll is a pure, hand-verified calculation engine (`payroll-calculator.ts`) doing real Indian statutory math — PF (12%/12%, ₹15,000 wage ceiling), ESIC (0.75%/3.25%, ₹21,000 gross ceiling), new-regime TDS (₹75,000 standard deduction, full slabs, §87A rebate, 4% cess), and a generic (non-state-specific) 2-tier Professional Tax — against a flat `monthlyBasic` per employee (no CTC/component catalog; HRA is a fixed 40% of basic, special allowance is always 0 since there's no data to derive it from). Run lifecycle collapses the spec's 9 states to 4 (Draft → Processed → Approved → Closed); reprocessing is allowed pre-approval and locked out after (verified: a 409 on reprocessing a Closed run). Employees missing a compensation record are never blocking — they surface in run results with `hasException: true` and a note, which is exactly how the demo data is seeded (Sneha Reddy, Draft status, intentionally has no compensation record). Payslips are visible to the employee only once a run is Approved/Closed — Draft/Processed numbers never leak to self-service. Approving a run fires a real in-app notification per non-exception employee. Frontend: attendance self-service page (mark + month calendar + manager's team-for-a-day card) and a payroll admin workspace (compensation form + run cockpit + result drill-down, gated both by hiding the nav item and by a friendly restricted-access message on direct URL access — the backend's 403 is the real gate either way); T-001's Attendance and Payslip KPIs are now live. Verified end to end through both curl and the actual browser UI, across two different logged-in users (Rohit, self-service; Priya, org_admin): compensation set for Rohit (Priya deliberately left unset) → run created → processed (Priya flagged as an exception, Rohit fully calculated matching hand-verified math exactly) → approved (Rohit notified) → closed (reprocessing correctly rejected with 409) → Rohit's payslip and T-001 KPIs show the real net pay in the browser; cross-tenant RLS isolation re-confirmed on every new endpoint against the globex tenant.
- **Phase 6 complete (MVP Completion)**: Requisition/Candidate/Application/Offer models (recruitment) and OnboardingCase/OnboardingTask models (onboarding) under RLS. Recruitment is a linear Draft→Approved→Published→Closed requisition lifecycle and a Draft→Approved→Issued→Accepted/Declined→Converted offer lifecycle (collapsed from the specs' larger state machines — see each model's schema.prisma comment); accepting-and-converting an offer creates a real Draft Employee (synthetic `NH-####` code), a login-capable User (`roles: ["employee"]`, so the new hire can sign in via OTP immediately), and an OnboardingCase with a fixed 4-item checklist — no configurable checklist templates, no candidate portal, no document upload/review sub-workflow. Onboarding activation is blocked while any blocking task is still `NotStarted` (verified: 409, then cleared by waiving/completing), and activation flips the linked Employee to Active in the same action. Reports v1 is a fixed set of live cross-module KPI queries (headcount, today's attendance, pending leave, recruitment funnel, onboarding readiness, latest closed payroll run's cost) — not the configurable report-builder from the analytics-and-bi spec; this required exporting several repositories/services (`LeaveRequestRepository`, `LeaveBalanceService`, `PayrollRunRepository`, `PayslipService`, `AttendanceService`, `RequisitionRepository`, `ApplicationRepository`) that earlier phases had kept module-private. Bulk employee import validates and creates each CSV row independently (one bad row doesn't block the rest) by running class-validator manually per row instead of through the global pipe, which would otherwise 422 the whole batch on the first bad row. Ridz is a real AI-gateway module: `AiProvider` interface + `StaticDevAiProvider` (same swap-in contract as `OtpProvider` — keyword matching over real tenant-data queries, no external API key required; a real Claude API provider is a drop-in behind the same interface using `AiDataService` as its tool layer) wired to the actual chat panel on T-001, answering leave balance / today's attendance / team attendance / latest payslip / headcount from live data. Two real bugs were found and fixed during end-to-end verification, not left for later: (1) `OfferService.convert()`'s catch-all around user creation was silently swallowing a transient DB error as a false "duplicate email" — narrowed to only swallow the actual Prisma P2002 case, everything else now propagates; (2) `EmployeeService.create()` passed date-only strings straight to Prisma without `new Date(...)` conversion, which crashed on `joiningDate` — a latent bug from Phase 2 that bulk import was simply the first flow to exercise with that field populated, now fixed for both the single-add and bulk paths. Verified end to end via curl and the browser: full requisition→candidate→application→offer→conversion chain driven from the actual pipeline UI; onboarding checklist completion and HR-side waive/activate with the 409 block surfaced correctly in the UI; Reports Hub and Bulk Import workbench both exercised live; Ridz answered every intent correctly for two different logged-in users. RLS re-verified (18/18) after the new tables.
- **Phase 8 in progress (Wave 4 new business modules)**: working through the ten zero-code Wave 4 modules one at a time per the user's direction. **Expense Claims done**: `ExpenseClaim` model under RLS (5-state, 9-state spec collapsed), submit/approve/reject/cancel/mark-paid with the same manager+admin-override RBAC pattern reused from Leave/Appraisals, manager-scoped and admin tenant-wide list views, `ExpenseHubPage` frontend. Reimbursements collapsed into the single admin mark-paid action. **Travel Requests done**: `TravelRequest` model under RLS (5-state, 7-state spec collapsed), same submit/approve/reject/cancel pattern plus admin-only mark-completed (stands in for the entire booking/travel-desk downstream flow), `TravelHubPage` frontend. **Asset Management done**: `Asset` catalog + `AssetAssignment` under RLS — a deliberately different shape from Expense/Travel (admin-driven assign/return, not an employee-request/approval flow, matching the spec's own IT/Workplace-Ops framing), collapsing both the Assignment and Return specs' state machines into a single Assigned→Returned transition with a `returnCondition` field, `AssetsHubPage` frontend (My Assets self-service + admin catalog/assign/return). All three verified end to end via curl and the browser. **Remaining from the original ten**: Expense, Travel, Asset, Employee Experience, Helpdesk, Contractor, Communication, Visitor and Workplace, and Health Safety and Wellness are now all done (see their own phase entries below); only Document Management is still not started.
- **Phase 9 complete (Wave 1 Organization Management, full deepening)**: per the user's explicit direction to finish every remaining Organization Management sub-capability (not just a v1 slice), 13 new models under RLS consolidate the full catalog — `Company` (+holding hierarchy/branding/fiscal calendar), `OrgUnit` (business unit/division/section-team/branch/region/zone/territory/campus/building/floor/work-area/location, one type-tagged table), `FinancialCenter` (cost center/profit center/project, another type-tagged table), `ReportingLine` (supplementary dotted/matrix/acting lines alongside the existing `Employee.managerId` primary line), `JobFamily`→`JobFunction`→`Designation` (career track folded in), `Grade` (band folded in), `Position` (a real catalog gap with no spec at all — modeled as a departmental seat), `WorkCalendar`+`WorkCalendarDay`+`WorkCalendarAssignment` (holiday calendar folded in as a day type), and `OrgPolicy` (another real catalog gap). Organization tree is a computed `GET /org/tree` read-only assembly, not a new table. New `OrgSettingsPage` frontend (nine sections) stands in for the not-yet-designed T-016 Organization Explorer board. Verified end to end via curl (full chain including duplicate/missing-reference error handling, state-conflict 409s, and cross-tenant RLS isolation) and the browser (every section renders live data; a real click-through creation fired a genuine 201).
- **Phase 7 complete (Wave 3 remainder: Performance, Learning, Talent, Compensation Planning)**: Goal/Appraisal models (performance), LearningCourse/LearningEnrollment models (learning), TalentAssessment model (talent), CompensationReviewCycle/CompensationReviewItem models (compensation planning) — all under RLS. Goals are employee-authored directly into Active status (no draft/approve step, no cascading from enterprise goals, no milestones — progress is a single updatable percentage + note). Appraisals are self-review→manager-review→finalize only (no skip-level, no calibration, no disputes), with the existing manager/admin-override permission pattern reused from leave approvals. Learning is a flat admin-managed course catalog (Draft→Published→Archived) with self-enrollment only (Enrolled→Completed/Withdrawn) — no programs/pathways/cohorts/sessions/assessment scoring; a withdrawn enrollment cannot currently re-enroll (the `[tenantId, employeeId, courseId]` unique constraint is permanent in v1, a documented limitation). Talent is a single directly-editable 9-box placement per employee per period (performanceRating 1-5 bucketed into Low/Medium/High bands × potentialRating Low/Medium/High) entered by org_admin/hr_ops — no review cycles, calibration sessions, or confidential-note segmentation; every route is admin/hr-ops gated with no employee self-service view, per the spec's confidentiality requirement. Compensation Planning is one review cycle per period year (Open/Closed) holding one Proposed→Approved→Applied item per employee — no budget pools, guideline matrices, or exception routing; "Apply" writes straight through to the existing `EmployeeCompensation` via the (newly exported) `CompensationRepository`, with `currentMonthlyBasic` captured as an immutable snapshot at proposal time rather than live-recomputed. **Explicitly deferred, not started**: Succession Planning (`13-talent-management/01-succession-planning.md`) — no slates, no successor linkage from the 9-box; Benefits Administration and Flexible Benefits (`14-compensation-and-benefits/04` and `05`) — no enrollment, elections, or carrier integration; the broader Salary Reviews spec (`14-.../02-salary-reviews.md`) — collapsed entirely into the single Merit Cycles slice, no separate market-data/banding workflow; and the LMS content engine (sessions, attendance, assessments, external-import verification, multi-language metadata) from the learning spec. Verified end to end via curl and the browser across all four sub-modules with two different logged-in users (Rohit, self-service; Priya, org_admin): goal creation and progress update on the actual Goals page; the full appraisal self-review→manager-review→finalize chain including a 403 permission-guard check and correct manager-scoped team visibility; course creation→publish→self-enroll→complete with a 409 on duplicate enrollment; two 9-box placements landing in the correct grid cells; and a full compensation-planning propose→approve→apply cycle whose Apply step was confirmed live on the Payroll page to have actually updated the employee's real compensation record. RLS re-verified: all 7 new tables show `relrowsecurity`/`relforcerowsecurity` true, and Alex Carter (Globex tenant, org_admin) sees zero rows across all four new domains despite the Srijan Labs data clearly existing (26/26 tenant-scoped tables now enabled+forced).
